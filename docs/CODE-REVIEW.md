# 코드 리뷰 절차 및 기준 (SmartQnR)

모든 소스 변경은 **Pull Request(PR)** 를 통해 병합하며, **최소 1인 이상의 리뷰 승인**을 거칩니다.
GitHub PR 의 리뷰·승인·코멘트 기록이 곧 **코드 리뷰 수행 이력**이 됩니다.

## 1. 절차

1. **브랜치 생성** — 작업 단위별로 브랜치를 만든다. (`feat/…`, `fix/…`, `chore/…`)
2. **개발 + 자체 검증** — 커밋 전 로컬에서 다음을 통과시킨다.
   - `npm run format:check` · `npm run lint` · `npm run typecheck` · `npm run build`
3. **PR 생성** — `.github/pull_request_template.md` 양식을 채워 PR 을 연다.
4. **자동 검사(CI)** — `ci.yml` 이 포맷·린트·타입검사를, `build-exe.yml` 이 빌드를 자동 수행한다.
   - CI 가 하나라도 실패하면 리뷰 이전에 작성자가 수정한다.
5. **리뷰어 지정** — 작성자 외 1인 이상을 리뷰어로 지정한다.
6. **리뷰 진행** — 아래 기준·체크리스트에 따라 리뷰. 코멘트는 근거와 함께 남긴다.
7. **수정·재검토** — 지적 사항을 반영하고 다시 리뷰를 요청한다.
8. **승인(Approve) 후 병합** — 승인 + CI 통과 시에만 병합한다. (병합 후 브랜치 삭제)

## 2. 리뷰 기준

| 관점        | 확인 내용                                               |
| ----------- | ------------------------------------------------------- |
| 정확성      | 요구사항을 충족하는가, 엣지 케이스·에러 처리가 적절한가 |
| 가독성      | 이름·구조가 명확한가, 불필요한 복잡성은 없는가          |
| 일관성      | 코딩 컨벤션(idiomatic.js)·기존 코드 스타일을 따르는가   |
| 재사용성    | 중복 로직을 공통화했는가, 과도한 추상화는 아닌가        |
| 성능        | 불필요한 재렌더·연산·메모리 사용이 없는가               |
| 보안        | 입력 검증·권한 처리·민감정보 노출이 적절한가            |
| 테스트/검증 | 동작을 확인했는가(수동/자동), 회귀 위험은 없는가        |

## 3. 리뷰 체크리스트

- [ ] `format:check` · `lint` · `typecheck` · `build` 모두 통과
- [ ] 코딩 컨벤션(네이밍·구조·주석) 준수
- [ ] 변경 범위가 PR 목적에 부합(무관한 변경 섞이지 않음)
- [ ] 예외·에러·로딩·빈 상태 처리
- [ ] 하드코딩(색상·문자열 등) 대신 테마·상수·설정 사용
- [ ] 접근성·다크모드 등 UI 일관성 유지
- [ ] 개인정보/보안상 문제 없음

## 4. 이력 관리

- 리뷰 이력은 GitHub PR(리뷰 코멘트·Approve·변경 요청)에 남는다.
- 산출물 제출이 필요할 경우, PR 목록/리뷰 내역을 내보내(Export) 근거로 첨부한다.
